# proto-flow

Rust bindings for Flow's protobuf definitions: the built-spec types of
`flow.proto`, the `capture` / `derive` / `materialize` connector protocols,
the `connector` multiplexing protocol, and the `ops`, `runtime`, and `shuffle`
protocols. Bindings are **checked in** under `src/`, and regenerated by
`mise run build:rust-protobufs` (which builds this crate with its `generate`
feature and then runs `cargo fmt`). Never hand-edit `src/*.rs`.

`src/lib.rs` also carries the small amount of hand-written surface:
`AnyBuiltSpec`, the `*_json` serde adapters used by the generated code, and
`RawJSONDeserialize`.

## Key files

- `build.rs` — the generator. prost produces `src/<pkg>.rs`, pbjson produces
  `src/<pkg>.serde.rs`, and a final pass of regexes rewrites the pbjson output
  (see below).
- `src/internal.rs` — `get_internal` / `set_internal` / `with_internal` over
  the `internal: Bytes` field carried by connector Requests and Responses.
- `src/linked.rs` — accessors which resolve a binding or transform to its
  `CollectionSpec` over both the inlined and `collection_index` encodings.
- `tests/regression.rs` — snapshots the JSON and wire encodings of every
  message we care about, plus a `size_of` table. These snapshots are the
  contract: a diff in one means the encoding changed.

## Non-obvious details

### The injected `oneof kind`

`capture`, `derive`, and `materialize` each declare `Request` and `Response`
as a flat struct of optional sub-message fields, even though exactly one of
those fields is ever set. That shape suits Go, whose sub-messages are pointers
anyway, but in Rust prost embeds each sub-message *by value*: a `Request` is
then as large as the sum of all its variants, and the runtime pays real memory
bandwidth to move one around.

So `build.rs` rewrites the descriptor set before generating code. It calls
`prost_build::Config::load_fds` (which runs protoc), passes the result through
`inject_oneofs`, and then hands the rewritten set to `compile_fds`. The
rewrite gathers each message's sub-message fields — everything but `internal`,
which stays a plain sibling — into a `oneof` named `kind`, so the generated
Rust is `pub kind: Option<request::Kind>` with `request::Kind::Open(..)`.

Three things make this safe rather than clever:

- **The wire and JSON encodings do not change.** A protobuf `oneof` encodes
  exactly as the optional fields it gathers, and pbjson flattens variants back
  into the parent JSON object under the same keys. The regression snapshots
  are unchanged across the rewrite, which is how we know. (The one behavior
  change: JSON that sets two variants of one message is now rejected as a
  duplicate field, where before the last one won.)
- **The field lists are explicit**, in the `ONEOFS` table at the top of
  `build.rs`. **When you add a sub-message field to one of these six messages,
  add it to that table.** `inject_oneofs` panics if a listed field is missing
  or isn't a singular message, and — the point of the guard — if the message
  has a singular message field that is neither listed nor named `internal`.
  A new field cannot silently fall outside the enum.
- **Go is untouched, deliberately.** The `.proto` files are unchanged apart
  from comments, so this is a Rust-only binding change. Go already represents
  sub-messages as pointers, so a oneof would save it ~30 bytes per message
  while adding a wrapper allocation per decode, type switches at every read
  site, and renamed wrapper types across ~130 call sites in the `connectors`
  repo. There is no payoff there.

`inject_oneofs` also synthesizes a `SourceCodeInfo` location for each oneof it
adds: prost-build looks one up unconditionally and panics when it's absent.
Its leading comment becomes the doc comment on the generated field and enum.

`crates/proto-grpc` compiles the same `.proto` files but maps every message
through `extern_path` to `::proto_flow::*`, so it generates only service stubs
and is unaffected by any of this.

### pbjson fixups

pbjson's output is post-processed by regex in `build.rs`:

- Fields ending `_json`, `_json_map`, and `_json_vec` hold JSON documents as
  `Bytes`. pbjson would base64 them; the fixups serialize them as `&RawValue`
  and deserialize through `RawJSONDeserialize`.
- Stats counters (`bytesTotal`, `docsTotal`, `bytesBehind`) are `u64`, which
  pbjson would quote per proto3 JSON rules. We emit them as JSON numbers.

Those two match named struct fields (`self.foo_json`), so the oneof variants —
all message-typed — are outside their reach. A third rewrites the oneof arms
themselves:

- pbjson's `visit_map` rejects a variant key whose sibling is already set
  *before* it reads the value, which conflates a present key with a present
  value. ProtoJSON requires a `null` field to parse "as though it was not
  present in the input at all", and a connector which models the message as a
  struct of optional fields — which is what the `.proto` declares — sends
  exactly that: `{"opened":{},"published":null}`. The fixup parses the value
  first and ignores a null, so that only two *occupied* variants are a
  duplicate. `test_kind_null_siblings` pins both halves.

pbjson serializes a oneof only through its parent message, so `build.rs` also
appends an `impl serde::Serialize` for each injected `Kind` enum. A bare `Kind`
serializes exactly as its parent would with an empty `internal` — `{"open":
{..}}` — which lets a caller report a mis-matched variant without hauling the
whole message along. There is no `Deserialize`: the parent message is the only
decoding entry point.
