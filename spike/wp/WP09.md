## Steps
Experiment 9:
- Policy with `declaredCidrs: [{cidr: 198.51.100.10/32, ports: [443]}]`.
- Guest workload (`--exec` a python script under the venv dir): one HTTPS
  request per new connection to `https://198.51.100.10/probe`, paced at 50
  per second, for 10 minutes, verifying the cert is skipped (self-signed).
  Log achieved rate per 10-second window.
- Sample the helper's cgroup every 10 seconds: `cpu.stat` usage_usec,
  `memory.current`, thread count from `/proc/<shim>/status`. Report start,
  end, and the time series.

Experiment 10:
- Idle guests: derive-python image, `--exec sleep infinity`, `memoryMib
  512`, vcpus 1. Launch one at a time until host `MemAvailable` drops below
  20%. For each: `memory.current`, threads, and after all are up, the total
  host delta from `free`.
- Reclaim: in a guest, `--run-as-root --exec sh -c 'cat big-file > /dev/null;
  echo 3 > /proc/sys/vm/drop_caches; sleep infinity'` and watch that
  helper's `memory.current` before and after the drop. Free-page reporting
  is on by default in libkrun; this shows whether it returns memory.
- Overhead constant: for a handful of guests, read guest `MemTotal -
  MemAvailable` from `/proc/meminfo` (via a periodic `--exec` reporter) and
  subtract from the helper's `memory.current`. Report the distribution; the
  launcher's `FLOW_SANDBOX_SPIKE_MEMORY_OVERHEAD_MIB` default gets set from
  it.
- TLS-holding variant: 20 guests each opening one TLS connection to nginx
  and sleeping. Same measurements.
- Whole density pass once with `--thp-disable` and once without.

## Facts from WP10
- **Sample host `MemAvailable` only after a host `sync`.** Dirty page cache
  counts against it until written back; a guest that just wrote a gigabyte
  reports the disk being behind as memory spent. This bites experiment 10's
  "launch until `MemAvailable` drops below 20%" directly.
- **A guest touching its own RAM is the largest term.** At `--disk-mib 1024`
  WP10 saw `MemAvailable` fall by almost exactly the bytes written, and the
  cause was the 1 GiB guest touching its own 1 GiB, not the disk. Separate
  the two before attributing anything to the helper.
- **podman tears down after its client has returned.** Container removal,
  netns teardown and layer reclaim are asynchronous to `podman kill` and to a
  `--rm` exit. Any "afterwards" measurement, including density's host delta
  after guests are torn down, must poll for quiescence (9 s of settle in one
  WP10 arm).
- **Do not scrape guest stderr under `--debug`.** The console tee and the
  workload's stderr share one descriptor and interleave below line
  granularity; flow-init's timing lines lose their prefixes. The periodic
  `--exec` reporter for the overhead constant must run without `--debug`.
- **The helper's cgroup limit is `--memory-mib + 256`** as the spike switch
  sets it today; the overhead constant this package measures replaces that
  256. The guest root's writable layer is
  `overlay-containers/<container id>/userdata/overlay/<n>/upper`, not
  anything `podman inspect` reports, should a density pass need to account
  for it.

## Facts from WP06
- One `flowctl preview --sessions 1` starts a capture connector twice
  (validate, then open). If you count launches, one preview is two.
- Guest stderr reaches the host ~290 ms late through libkrun's console. Time
  in-guest events with the guest's clock, never by host arrival.
- Fresh boot per data point, or name the regime (WP08b's method note): a
  first operation in a guest includes memory first-touch.
